# UI/UX 가이드

이 문서는 **사용자를 다음 단계로 넘기는 설계**만 다룬다. 색·타입·간격 같은 시각 언어는 [DESIGN.md](./DESIGN.md), 화면 전이와 엣지 케이스의 사실 관계는 [USER_JOURNEY.md](./USER_JOURNEY.md), 데이터 경계와 게이팅 규칙은 [plan.md](../plan.md)에 있다. 여기서는 **같은 전이를 왜 그 순서와 밀도로 놓는가**를 적는다.

## 1. 출처

[Figma UI Design Principles](https://www.figma.com/ko-kr/resource-library/ui-design-principles/)의 7원칙을 기준으로 삼는다. 다만 원문은 일반론이므로 **TxAnalyzer의 제약으로 번역된 것만** 규칙으로 남긴다.

| 원칙 | TxAnalyzer 번역 | 절 |
|---|---|---|
| 계층 구조 | 한 화면에 주 CTA 1개. 나머지는 전부 부차 | §3 |
| 점진적 공개 | 여정을 6개 관문으로 쪼개고, 관문마다 결정을 1개만 요구한다 | §2 |
| 일관성 | 같은 목적지는 같은 라벨, 같은 상태는 같은 문구 | §10 |
| 대비 | 파랑(`#0052ff`)은 "다음 단계" 전용 신호다 | §3 |
| 접근성 | 비동기 상태 변화를 스크린리더에 알린다 | §11 |
| 근접성 | 판단과 그 판단의 근거를 같은 카드에 둔다 | §7 §8 |
| 정렬 | 1200px 폭과 4px 배수 그리드 (DESIGN.md §3) | — |

원문이 답하지 않아 **우리가 정하는 것**: 비동기 대기(§6), 잠금 티저(§8), 금융 데이터 고지(§4).

## 2. 전진 모델 — 6개 관문

여정은 6개의 관문으로 나뉜다. 각 관문은 사용자에게 **결정을 하나만** 요구한다.

| 관문 | 넘어야 하는 것 | 최대 이탈 원인 |
|---|---|---|
| G1 랜딩 → 로그인 | "내 카드 내역을 넘겨도 되는가" | 신뢰 |
| G2 로그인 → 대시보드 | Google 버튼 1회 | 낮음 |
| G3 대시보드 → 업로드 | **CSV를 어디서, 어떤 형태로 구하는가** | 활성화 병목 |
| G4 업로드 → 결과 도달 | 최대 4분의 비동기 대기 | 대기 이탈 |
| G5 결과 → 이해 | 5개 카드를 읽는 순서 | 인지 부하 |
| G6 티저 → Pro | 월 $9 지불 결정 | 전환 |

두 가지 전제:

1. **관문당 결정 1개.** 한 화면이 두 가지를 동시에 물으면 사용자는 둘 다 미룬다. 업로드 화면에서 요금제를 묻지 않고, 결과 화면에서 새 업로드를 재촉하지 않는다.
2. **모든 관문은 되돌아갈 수 있다.** 되돌아갈 수 없는 지점은 계정 삭제 하나뿐이며, 그 하나만 확인 절차를 갖는다.

## 3. 계층 구조 — 화면당 주 CTA 1개

파랑 알약 버튼은 **그 화면에서 사용자가 다음에 할 일** 하나에만 쓴다. DESIGN.md §2의 "한 밴드당 파랑 1~2회"를 여정 관점으로 다시 쓰면 아래 표가 된다.

| 화면 | 주 CTA (파랑) | 부차 (테두리·링크) | 두지 않는 것 |
|---|---|---|---|
| 랜딩 | 시작하기 | 분석 항목 · 요금제 앵커, 내비 로그인 | 뉴스레터, 문의, 소셜 |
| `/login` | Google로 로그인 | 약관·개인정보 링크 | 이메일 가입, 게스트 체험 |
| 대시보드 (이력 없음) | 업로드 | 없음 | 히스토리·설정 강조, 요금제 배너 |
| 대시보드 (이력 있음) | 업로드 | 히스토리 행, 설정, 결제 관리 | 상단 고정 업그레이드 바 |
| 분석 대기 중 | 없음 (버튼 비활성) | 히스토리 열람 | 취소 버튼 |
| 리포트 | 없음 | 재시도(부분 완료 시) | 공유, 내보내기 |
| 잠금 티저 카드 | 업그레이드 | 없음 | 전역 배너 |
| 업그레이드 모달 | 업그레이드 | 닫기 | 세 번째 선택지 |

리포트 화면에 주 CTA가 없는 것은 의도다. 결과를 읽는 것 자체가 그 화면의 목적이고, 다음 행동(업그레이드)은 §8의 티저 카드 안에서만 제안한다.

## 4. G1 — 랜딩: 유치 설계

히어로가 3초 안에 답해야 하는 질문은 셋이다.

1. **무엇을 넣나** — CSV 거래 내역
2. **무엇이 나오나** — 다섯 가지 분석
3. **내 데이터는 어떻게 되나** — 원본 CSV를 보관하지 않는다

1과 2는 히어로 카피와 `ProductPreview`가 답한다. **3은 히어로 밴드 안에서 답한다.** 금융 데이터를 다루는 제품에서 이 문장은 각주가 아니라 유치 논거이며, 푸터에 두면 결정 시점에 읽히지 않는다(근접성).

규칙:

- **CTA 라벨은 도착지와 어긋나지 않는다.** "시작하기"가 로그인 화면으로 간다면 버튼 아래 캡션으로 `Google 계정으로 로그인합니다`를 병기한다. 기대와 다른 화면이 나오는 것이 첫 이탈 사유다.
- **가격을 로그인 뒤로 숨기지 않는다.** 요금제 표는 로그인 앞에 둔다. Pro 열은 리본이나 색 테두리가 아니라 다크 표면으로 반전한다(DESIGN.md §4).
- **Free로 무엇을 할 수 있는지 랜딩에서 확정한다.** "월 5회, 최근 12개월"은 제약이 아니라 진입 장벽을 낮추는 사실이므로 그대로 적는다.
- 랜딩의 모든 주 CTA는 `/login` 하나로 모은다. 목적지가 하나면 라벨도 하나여야 한다(§10).
- 스크롤 순서는 고정이다: 히어로 → 분석 항목 5 → 요금제 → CTA 밴드 → 푸터. 사용자가 목표에 도달하는 논리적 순서이며, 요금제가 분석 항목보다 앞에 오면 아직 가치를 모르는 상태에서 가격을 본다.

**G2(로그인)** 는 화면에 Google 버튼 하나, 약관 캡션 하나만 둔다. 이 화면에서 새로 묻는 것을 만들지 않는다 — 이름·업종·설문은 전부 전환을 깎는 추가 관문이다.

## 5. G3 — 첫 업로드: 활성화 설계

**활성화의 실제 장벽은 UI가 아니라 CSV 확보다.** 사용자는 업로드 박스가 무엇인지는 알지만, 자기 카드 내역을 CSV로 어떻게 꺼내는지는 모른다. 빈 상태에 드롭존만 두면 여기서 멈춘다.

점진적 공개는 **정보를 숨기는 것이 아니라 순서를 정하는 것**이다. 첫 업로드 화면은 다음을 같은 화면에서 답한다.

- 받는 형식: `CSV`, `4MB 이하`, `UTF-8`
- 필요한 컬럼: `날짜 · 내용 · 금액`
- 한 파일에 한 통화
- 전송 고지: 분석을 위해 일부 데이터가 Anthropic API로 전송되고, 원본 CSV는 보관하지 않는다는 사실 (CLAUDE.md, PRD.md 요구사항)

**실패 문구가 사전 요구사항을 사후에 알려주는 구조를 피한다.** `encoding_error`, `column_mapping_failed`, `mixed_currency`는 전부 업로드 전에 한 줄로 예고할 수 있는 조건이다. 드롭존 아래 캡션 한 줄이 실패 한 번보다 싸다.

카드사·은행별 다운로드 경로 안내는 넣지 않는다 — 전용 포맷 파서가 PRD의 MVP 제외 항목이므로, 특정 카드사를 안내하면 지원하지 않는 포맷을 약속하는 셈이 된다. 필요해지면 §14에 따라 이 문서에 추가한다.

빈 상태 자체는 DESIGN.md §9를 따른다: 사실의 평서문 한 줄 + 주 CTA 1개, 일러스트 없음.

## 6. G4 — 비동기 대기: 이탈 설계

업로드는 `202 + uploadId`로 즉시 반환되고 분석은 `after()`에서 진행된다. UI는 2초·4초·이후 5초 간격으로 폴링하고 2분 뒤 멈춘다. 내부 deadline은 240초다.

즉 **사용자는 결과를 최대 4분간 기다리며, 화면을 닫아도 분석은 계속된다.** 이 사실이 이 관문의 설계를 전부 결정한다.

- **진행률 바를 쓰지 않는다.** 남은 시간을 알 수 없으므로 진행률은 거짓말이 된다. 대신 상태값이 이미 단계를 표현한다: `파일 읽는 중` → `분석 중`. Figma 원문의 "남은 단계를 파악하게 하라"는 조언은 여기서 퍼센트가 아니라 **단계 이름**으로 구현한다.
- **"닫아도 된다"를 2분 전에 말한다.** 2분 초과 문구(`분석은 계속됩니다. 나중에 다시 확인하세요.`)는 이미 이 역할을 하지만, 이탈 불안은 대기 시작 직후에 생긴다. 대기 문구는 처음부터 결과가 보존된다는 사실을 포함한다.
- **취소 버튼을 만들지 않는다.** 중단해도 한도는 이미 차감됐고 되돌릴 것이 없다. 누를 수 있지만 아무것도 개선하지 않는 버튼은 두지 않는다.
- **대기 중 다른 조작을 막지 않는다.** 히스토리 열람은 열어 두고, 동시 분석이 1건이므로 새 업로드 입력만 비활성화한다. 화면 전체를 덮는 오버레이를 쓰지 않는다.
- 스켈레톤을 쓰지 않는다(DESIGN.md §9). 스켈레톤은 곧 나타날 콘텐츠의 형태를 약속하는데, 실패로 끝날 수도 있다.

**부분 완료(`partial`)는 전진으로 취급한다.** 집계 카드 4장은 정상 렌더하고 해석 카드에만 재시도 버튼을 둔다. 화면 전체를 실패로 처리하면, 이미 성공한 계산 결과를 사용자에게서 빼앗는 것이 된다.

## 7. G5 — 결과 읽기 순서

카드 5장은 **사실 → 해석 → 행동** 순으로 배치한다. 현재 순서가 이 원칙과 일치한다.

| 순서 | 카드 | 성격 | 근접성 규칙 |
|---|---|---|---|
| 1 | 카테고리별 지출 | 사실(코드 집계) | 금액과 비중을 같은 행에 |
| 2 | 월별 추이 | 사실(코드 집계) | 축 레이블과 값을 붙여서 |
| 3 | AI 요약 | 해석(LLM) | 실패 시 재시도 버튼을 카드 안에 |
| 4 | 이상 거래·구독 누수 | 해석(LLM) | 후보와 그 근거를 같은 항목에 |
| 5 | 절약 인사이트 | 행동 | 업그레이드 CTA를 이 카드 안에 |

- 헤더에는 조회 범위(`최근 12개월` / `전체 기간`)와 총액을 둔다. **범위를 먼저 읽어야 아래 숫자의 의미가 정해진다.**
- `skippedRowCount`가 0이 아니면 결과 상단 캡션으로 알린다. 결과를 다 읽은 뒤 하단에서 알면 읽은 것을 다시 의심하게 된다.
- 해석 카드는 마크다운·HTML을 렌더하지 않는다(CLAUDE.md CRITICAL). 항목이 여럿이면 목록 문법이 아니라 **배열 원소 하나당 컴포넌트 하나**로 그린다(DESIGN.md §10).
- 숫자는 전부 Mono, 증감은 부호와 색을 함께 쓴다(DESIGN.md §6). 색만으로 방향을 전달하지 않는다.

## 8. G6 — 티저에서 전환으로

서버(`get_upload_report()`)가 응답에서 필드를 아예 제외하므로 **UI는 "가려진 데이터"가 아니라 "없는 데이터"를 그린다**(DESIGN.md §7).

이 제약이 오히려 전환 설계를 단순하게 만든다.

- **티저의 설득력은 전부 실제 총 건수에서 나온다.** `12건 발견 · 3건 표시`는 서버가 계산한 참값이다. 블러 처리한 가짜 숫자나 자물쇠 아이콘은 이 참값보다 설득력이 낮고, 신뢰를 깎는다.
- **업그레이드 CTA는 티저 카드 안에만 둔다.** 사용자가 "더 있다"는 사실을 확인한 바로 그 자리가 결정 지점이다(근접성). 전역 배너나 상단 고정 바는 맥락이 없는 자리에서 조르는 것이므로 만들지 않는다.
- **모달은 결정을 하나만 묻는다.** 무엇이 열리는지 한 줄, 가격, 업그레이드, 닫기. 그 이상을 넣지 않는다.
- **업그레이드 직후에는 재분석 없이 같은 리포트의 `full`이 열린다.** 결제에서 돌아온 사용자는 **결제를 유발한 그 리포트**로 복귀해야 한다. 대시보드 최상단으로 보내면 방금 지불한 대가를 사용자가 직접 찾아야 한다.
- **취소하고 돌아온 경우 구독 상태는 불변이며 화면도 불변이다.** 재시도를 재촉하지 않는다.
- **다운그레이드는 조용히 재잠금한다.** 같은 payload가 보존되고 응답만 `recent12m` + 티저로 돌아간다. 데이터가 삭제된 것처럼 보이는 문구를 쓰지 않는다.

## 9. 실패에서의 전진

**모든 에러는 다음 행동을 하나 준다.** 문구는 DESIGN.md §9가 진실의 원천이고, 여기서는 그 문구에 붙는 행동만 정한다.

| code 그룹 | 다음 행동 | 버튼 |
|---|---|---|
| `file_too_large` · `invalid_file_type` · `empty_file` · `encoding_error` | 같은 화면에서 다른 파일 선택 | 없음 (드롭존 유지) |
| `parse_failed` · `column_mapping_failed` · `mixed_currency` · `unsupported_transaction_semantics` | 원본을 보관하지 않으므로 **재업로드** | 없음 (드롭존 유지) |
| `analysis_timeout` · `analysis_failed` (`partial`) | 저장된 transactions로 **재시도** | 다시 시도 |
| `retry_limit_exceeded` | 재업로드 | 없음 |
| `upload_limit_reached` | 업그레이드 또는 다음 달 대기 | 업그레이드 |
| `analysis_in_progress` | 진행 중인 분석 결과로 이동 | 없음 |
| `not_found` | 히스토리로 | 없음 |
| `unauthorized` | 로그인 후 원래 화면 복귀 | 로그인 |

- **재시도할 수 없는 실패에 재시도 버튼을 두지 않는다.** 파싱 전 실패는 원본이 없어 구조적으로 재시도가 불가능하다. 누르면 실패하는 버튼은 두 번 실망시킨다.
- `message` 문자열이 아니라 `code`로 분기한다.
- 에러 문구에 이모지·느낌표·사과를 쓰지 않는다(DESIGN.md §11).

## 10. 일관성 — 라벨과 문구

**같은 목적지는 같은 라벨.** 라벨이 다르면 사용자는 다른 곳으로 간다고 읽는다.

| 역할 | 형태 | 라벨 |
|---|---|---|
| 전진 | 파랑 알약 | `시작하기` · `업로드` · `업그레이드` · `다시 시도` |
| 부차 | 테두리 알약 | `닫기` · `로그아웃` |
| 이동 | 텍스트 링크 | `설정` · `결제 관리` · `개인정보 처리방침` · `이용약관` |

- 신규 유입 CTA는 **하나의 라벨로 통일한다.** 내비의 `로그인`만 예외로 둔다 — 재방문자를 위한 다른 의도이기 때문이다.
- **상태 문구는 DESIGN.md §9가 진실의 원천이다.** 코드와 문서가 다르면 코드를 문서에 맞춘다.
- **한 가지 문체만 쓴다.** DESIGN.md §11의 "차분한 금융 기관의 말투"는 `합니다`체를 뜻한다. `~했어요`, `~걸려요` 같은 해요체를 섞지 않는다. 문체가 흔들리면 같은 제품이 두 명처럼 말한다.
- 버튼은 동사로 끝나는 2~5자.

## 11. 접근성 — 여정 관점

DESIGN.md §12(대비·포커스 링·라벨)에 더해, **흐름에서만 생기는 문제**를 여기서 정한다.

- **비동기 상태 변화는 `role="status"`로 알린다.** 화면을 보고 있지 않은 사용자에게 `queued → parsing → analyzing → completed` 전이는 침묵이다.
- **포커스는 흐름을 따라간다.** 업로드 시작 후 상태 영역으로, 모달이 열리면 모달 안으로, 닫히면 열었던 버튼으로 되돌린다.
- **모달은 Esc로 닫히고 포커스가 안에 갇힌다.** 업그레이드 모달은 결제로 이어지므로 키보드만으로 빠져나올 수 있어야 한다.
- **드롭존은 클릭 없이 동작한다.** 드래그 앤 드롭은 보조 수단이고, 키보드로 도달 가능한 파일 선택이 주 경로다.
- **전 여정이 키보드만으로 통과 가능해야 한다.** 랜딩 → 로그인 → 업로드 → 결과 → 업그레이드까지 마우스 없이 끝까지 간다.
- 에러는 색이 아니라 문구로 전달한다.

## 12. 하지 않는 것

결제를 받고 금융 데이터를 다루므로 아래는 규칙이 아니라 금지다.

- 가짜 블러 처리, 플레이스홀더 숫자, 자물쇠 아이콘으로 만든 잠금 연출
- 카운트다운, 잔여 수량, "N명이 보는 중" 같은 인위적 희소성
- 해지 경로를 숨기거나 단계를 늘리는 것 — Polar 포털 링크는 설정에서 한 번에 닿는다
- 취소 버튼을 회색 텍스트로 약화시키고 결제 버튼만 강조하는 대비 조작
- 법적 고지와 데이터 전송 고지를 접거나 흐리게 두는 것 (DESIGN.md §11)
- 업로드 전 추가 관문(설문·전화번호·팀 초대)
- 이모지, 느낌표, 수익·투자 조언으로 읽힐 수 있는 표현

## 13. 관문별 성공 기준

분석 도구는 MVP 범위 밖이다. 아래는 **DB에서 SQL로 셀 수 있는 프록시**이며, 이것만으로 관문별 병목을 특정할 수 있다.

| 관문 | 프록시 | 출처 |
|---|---|---|
| G2 | 가입한 사용자 수 | Auth 사용자 |
| G3 | `csv_uploads` row가 1건 이상인 사용자 비율 | `csv_uploads` |
| G4 | `completed` + `partial` 비율 대 전체 업로드 | `csv_uploads.status` |
| G4 실패 원인 | `error_code`별 분포 | `csv_uploads.error_code` |
| G5 | 2회차 이상 업로드한 사용자 비율 | `csv_uploads` |
| G6 | `plan = pro` 비율 | `subscriptions` |

가장 먼저 볼 것은 **G3**다. 여기서 멈춘 사용자는 제품을 한 번도 본 적이 없으므로, 다른 어떤 개선보다 우선한다.

## 14. 정하지 않은 것

필요해지는 시점에 이 문서에 추가한다.

- **온보딩 투어·코치마크** — 화면이 사실상 3개(랜딩·대시보드·설정)뿐이라 지금은 불필요하다고 판단했다.
- **분석 완료 알림** — 이메일·푸시 채널이 없다. G4 이탈이 실제로 확인되면 그때 검토한다.
- **카드사별 CSV 내려받기 안내** — §5의 이유로 보류. 첫 사용자 피드백 이후.
- **모바일 업로드 경험** — 모바일 브라우저에서 CSV 파일 접근이 어렵다. 반응형 중단점은 `phases/0-mvp` step 10에서 정한다.
- **A/B 테스트, 애널리틱스 도입** — §13의 SQL 프록시로 시작한다.
