# Architecture Decision Records

## 철학
MVP 속도 최우선. 인증·결제·DB는 관리형 서비스(Supabase, Polar)에 위임하고 자체 구현을 최소화한다. 프로토타입에 필요 없는 최적화·추상화는 넣지 않는다.

---

### ADR-001: Next.js App Router 풀스택 채택
**결정**: 랜딩, 대시보드, 로그인, 결제, API를 하나의 Next.js 프로젝트에서 처리한다.
**이유**: 별도 백엔드 없이 한 프로젝트/한 배포로 MVP를 가장 빠르게 완성할 수 있고 Vercel 배포와 궁합이 좋다.
**트레이드오프**: 나중에 백엔드를 분리하려면 리팩터링이 필요하다.

### ADR-002: Supabase (Auth + Postgres + Storage) 채택
**결정**: 인증, DB, 파일 스토리지를 Supabase로 통합한다.
**이유**: 세 가지를 한 서비스로 해결해 구축 속도를 높인다.
**트레이드오프**: 벤더 종속성이 생긴다.

### ADR-003: Polar를 결제 처리자로 채택
**결정**: 구독 결제를 Polar(Merchant of Record)로 처리한다.
**이유**: 구독 청구와 글로벌 세금·인보이스를 대행해 컴플라이언스 부담을 줄인다.
**트레이드오프**: Stripe 대비 커스터마이징 자유도가 낮고 국내 결제수단은 지원하지 않는다.

### ADR-004: Claude API 단일 LLM 프로바이더
**결정**: 분석에 Claude API만 사용한다.
**이유**: 멀티 프로바이더 추상화 레이어 없이 구현을 단순화한다.
**트레이드오프**: 장애·정책 변경 시 대체 수단이 없다.

### ADR-005: Google OAuth 단일 로그인 수단
**결정**: 이메일/비밀번호 없이 Google OAuth만 지원한다.
**이유**: 비밀번호 재설정·이메일 인증 플로우를 통째로 없앨 수 있다.
**트레이드오프**: Google 계정이 없는 사용자는 가입할 수 없다.

### ADR-006: 범용 CSV 파서
**결정**: 특정 금융사 전용 파서 대신 범용 파서를 쓴다.
**이유**: 특정 포맷에 종속되지 않고 다양한 입력을 받는다.
**트레이드오프**: 전용 파서보다 정확도가 낮아 컬럼 추론 보정이 필요하다(ADR-012).

### ADR-007: 동기 처리 + 4MB 업로드 상한
**결정**: 분석 파이프라인을 비동기 잡 큐 없이 하나의 요청에서 동기 처리하고, 업로드 상한을 4MB로 둔다. 진행 표시는 SSE 없이 스피너로 한다.
**이유**: Vercel 함수는 Fluid compute 기본값으로 300초까지 실행되므로 20~60초 분석에 충분하다. Vercel 요청/응답 body 하드 리밋이 4.5MB라 업로드 상한이 이에 종속된다. SSE는 스트림 시작 후 상태 코드를 바꿀 수 없어 에러 처리 복잡도만 늘린다.
**트레이드오프**: 4MB를 넘는 CSV는 처리할 수 없고, 사용자는 최대 1분간 스피너를 본다.

### ADR-008: 업로드별 독립 리포트
**결정**: 업로드 1건 = 리포트 1건으로 저장하고, 여러 업로드를 합산하는 통합 뷰는 만들지 않는다.
**이유**: 중복 거래 판정 로직과 그에 딸린 엣지 케이스를 통째로 제거할 수 있다.
**트레이드오프**: 여러 파일을 가로지르는 장기 추이 분석이 불가능하다.

### ADR-009: 집계는 코드, LLM은 해석
**결정**: 금액 합계·추이·반복결제 탐지는 코드로 계산하고, LLM은 컬럼 매핑 추론·카테고리 분류·자연어 해석에만 쓴다.
**이유**: 금융 데이터에서 LLM에 산술을 맡기면 환각으로 합계가 틀릴 수 있다. 비용과 지연도 줄어든다.
**트레이드오프**: 분석 로직을 직접 구현해야 한다.

### ADR-010: 전원 생성 + 조회 시점 트리밍
**결정**: Free 사용자에게도 5종 분석을 모두 생성하고, 조회 시점에 서버가 응답 필드를 잘라 티저만 보여준다.
**이유**: 티저를 보여주려면 생성이 필요하고, LLM 1회 통합 호출이라 한계비용이 낮다. 업그레이드 즉시 과거 리포트가 열려 재분석이 불필요하다.
**트레이드오프**: Free 사용자분의 LLM 비용이 발생한다.

### ADR-011: 원본 CSV는 암호화 보관하되 재분석 전용
**결정**: 원본을 AES-256-GCM으로 암호화해 Storage에 보관하되 다운로드는 제공하지 않는다. 파생된 `transactions`는 RLS + Postgres at-rest 암호화로 보호한다.
**이유**: 집계 쿼리를 하려면 거래 데이터는 평문이어야 한다. 다운로드를 막으면 CSV 수식 인젝션 표면이 사라진다.
**트레이드오프**: 암호화 키는 env 단일 마스터 키라 로테이션이 불가능하다.

### ADR-012: LLM 컬럼 매핑 추론
**결정**: 컬럼 자동 인식은 헤더 + 샘플 3행을 LLM에 보내 추론하고, 수동 매핑 UI는 만들지 않는다.
**이유**: 이미 LLM 파이프라인이 있어 호출 하나로 불규칙 포맷 대응력이 오히려 좋아지고, 화면·상태·API가 늘지 않는다.
**트레이드오프**: 추론이 실패하면 사용자가 직접 고칠 방법이 없어 재업로드해야 한다.

### ADR-013: 배포를 구현 초기에 배치
**결정**: 목업 상태의 스캐폴딩을 만든 직후 Vercel preview 배포를 수행하고(step1), 기능 완성 후 production으로 승격한다.
**이유**: 배포 파이프라인·환경변수·OAuth 리다이렉트 설정 문제를 기능 구현 전에 드러낸다.
**트레이드오프**: Vercel 인증이 없으면 초기 step에서 바로 막힌다.
