# Architecture Decision Records

## 철학
MVP 속도 최우선. 인증·결제·DB는 관리형 서비스(Supabase, Polar)에 위임하고 자체 구현을 최소화한다. 프로토타입에 필요 없는 최적화·추상화는 넣지 않는다.

---

### ADR-001: Next.js App Router 풀스택 채택
**결정**: 랜딩, 대시보드, 로그인, 결제, API를 하나의 Next.js 프로젝트에서 처리한다.
**이유**: 별도 백엔드 없이 한 프로젝트/한 배포로 MVP를 가장 빠르게 완성할 수 있고 Vercel 배포와 궁합이 좋다.
**트레이드오프**: 나중에 백엔드를 분리하려면 리팩터링이 필요하다.

### ADR-002: Supabase (Auth + Postgres) 채택
**결정**: 인증과 DB를 Supabase로 통합한다. Storage는 쓰지 않는다.
**이유**: 둘을 한 서비스로 해결해 구축 속도를 높인다. 원본 CSV를 보관하지 않기로 했으므로(ADR-011) 파일 스토리지가 필요 없다.
**트레이드오프**: 벤더 종속성이 생긴다.

### ADR-003: Polar를 결제 처리자로 채택
**결정**: 구독 결제를 Polar(Merchant of Record)로 처리한다.
**이유**: 구독 청구와 글로벌 세금·인보이스를 대행해 컴플라이언스 부담을 줄인다.
**트레이드오프**: Stripe 대비 커스터마이징 자유도가 낮고 국내 결제수단은 지원하지 않는다.

### ADR-004: Claude API 단일 LLM 프로바이더
**결정**: 분석에 Claude API만 사용한다.
**이유**: 멀티 프로바이더 추상화 레이어 없이 구현을 단순화한다.
**트레이드오프**: 장애·정책 변경 시 대체 수단이 없다.

### ADR-005: Google OAuth 단일 로그인 수단
**결정**: 이메일/비밀번호 없이 Google OAuth만 지원한다.
**이유**: 비밀번호 재설정·이메일 인증 플로우를 통째로 없앨 수 있다.
**트레이드오프**: Google 계정이 없는 사용자는 가입할 수 없다.

### ADR-006: 범용 CSV 파서
**결정**: 특정 금융사 전용 파서 대신 범용 파서를 쓴다.
**이유**: 특정 포맷에 종속되지 않고 다양한 입력을 받는다.
**트레이드오프**: 전용 파서보다 정확도가 낮아 컬럼 추론 보정이 필요하다(ADR-012).

### ADR-007: `202 + after()` + 폴링, 4MB 업로드 상한
**결정**: `POST /api/analyze`는 durable upload row를 만든 뒤 `202 { uploadId }`로 즉시 반환하고, 분석은 Next.js `after()`에 등록해 백그라운드에서 수행한다. UI는 `GET /api/uploads/[id]`를 2초·4초·이후 5초 간격으로 폴링하고 2분 뒤 중단한다. 업로드 상한은 `4_000_000` bytes다. 잡 큐는 도입하지 않는다.
**이유**: 응답을 붙들고 있으면 탭을 닫는 순간 작업이 사라지고 결과를 복구할 수 없다. row를 먼저 만들고 `after()`로 넘기면 브라우저 생명주기와 분리되어 재방문 시 상태를 복구할 수 있다. Vercel 함수는 Fluid Compute Node.js runtime에서 300초까지 실행되므로 내부 deadline 240초로 충분하다. Vercel 요청/응답 body 하드 리밋이 4.5MB라 업로드 상한이 이에 종속된다. SSE는 스트림 시작 후 상태 코드를 바꿀 수 없어 에러 처리 복잡도만 늘린다.
**트레이드오프**: 4MB를 넘는 CSV는 처리할 수 없다. 폴링 때문에 완료 감지가 최대 5초 늦고, 진행률이 아니라 상태값만 보여줄 수 있다.

### ADR-008: 업로드별 독립 리포트
**결정**: 업로드 1건 = 리포트 1건으로 저장하고, 여러 업로드를 합산하는 통합 뷰는 만들지 않는다.
**이유**: 중복 거래 판정 로직과 그에 딸린 엣지 케이스를 통째로 제거할 수 있다.
**트레이드오프**: 여러 파일을 가로지르는 장기 추이 분석이 불가능하다.

### ADR-009: 집계는 코드, LLM은 해석
**결정**: 금액 합계·추이·반복결제 탐지는 코드로 계산하고, LLM은 컬럼 매핑 추론·카테고리 분류·자연어 해석에만 쓴다.
**이유**: 금융 데이터에서 LLM에 산술을 맡기면 환각으로 합계가 틀릴 수 있다. 비용과 지연도 줄어든다.
**트레이드오프**: 분석 로직을 직접 구현해야 한다.

### ADR-010: dual-scope 생성 + DB 함수 트리밍
**결정**: 업로드 시점에 `recent12m`과 `full` 두 scope의 집계와 해석을 모두 생성해 `analysis_results.payload`에 저장한다. 조회는 security-definer RPC `get_upload_report()`가 담당하며, 소유권과 현재 plan을 확인해 허용된 scope와 티저만 잘라서 반환한다. `transactions`와 `analysis_results`에는 authenticated role의 SELECT 권한을 주지 않는다.
**이유**: 티저를 보여주려면 생성이 필요하고, 해석이 1회 호출이라 한계비용이 낮다. 업그레이드하면 재분석 없이 같은 payload의 `full`이 즉시 열린다. 트리밍을 애플리케이션 코드에 두면 한 군데만 빠뜨려도 유료 데이터가 새므로, DB 권한으로 경계를 강제한다.
**트레이드오프**: Free 사용자분의 LLM 비용이 발생하고, payload가 두 배가 된다. 게이팅 로직이 SQL에 있어 애플리케이션 테스트만으로는 검증할 수 없다.

### ADR-011: 원본 CSV 비보관
**결정**: 업로드된 원본 CSV를 보관하지 않는다. 메모리에서만 처리하고 Storage와 DB 어디에도 쓰지 않는다. 파생된 `transactions`는 RLS + Postgres at-rest 암호화로 보호한다.
**이유**: 보관하지 않으면 지켜야 할 것이 없다. 앱 레벨 암호화, 마스터 키 관리와 로테이션 불가 문제, Storage 경로 traversal, 다운로드 시 CSV 수식 인젝션이 한꺼번에 사라진다. 재분석에 필요한 것은 정규화된 `transactions`이지 원본이 아니다.
**트레이드오프**: 컬럼 매핑·파싱 단계에서 실패하면 재시도할 수 없고 사용자가 재업로드해야 한다. 파싱 규칙을 나중에 고쳐도 과거 업로드를 다시 돌릴 수 없다.

### ADR-012: LLM 컬럼 매핑 추론 + 코드 의미 검증
**결정**: 컬럼 자동 인식은 헤더 + 최대 20개 대표 행을 LLM에 보내 추론하되, 추론 결과를 그대로 믿지 않는다. 코드가 전체 행에 매핑을 적용해 날짜·금액의 95% 이상이 파싱되고 소비 행의 부호 의미가 일관되는지 검증한 뒤에만 채택하고, 미달이면 `column_mapping_failed`로 실패시킨다. 수동 매핑 UI는 만들지 않는다.
**이유**: 이미 LLM 파이프라인이 있어 호출 하나로 불규칙 포맷 대응력이 좋아진다. 다만 매핑이 틀리면 모든 금액이 조용히 틀리므로, LLM 출력을 제안으로만 쓰고 판정은 결정론적 코드가 한다.
**트레이드오프**: 추론이 실패하면 사용자가 직접 고칠 방법이 없어 재업로드해야 한다. 95% 기준은 임의값이라 정상 파일을 거부할 수 있다.

### ADR-013: 배포를 구현 초기에 배치
**결정**: 목업 상태의 스캐폴딩을 만든 직후 Vercel preview 배포를 수행하고(step1), 기능 완성 후 production으로 승격한다.
**이유**: 배포 파이프라인·환경변수·OAuth 리다이렉트 설정 문제를 기능 구현 전에 드러낸다.
**트레이드오프**: Vercel 인증이 없으면 초기 step에서 바로 막힌다.

### ADR-014: 결제 활성화 전 Vercel Pro 전환 필수
**결정**: 개발·preview 기간에는 Hobby를 쓰되, Polar production 승인 직후 **결제를 켜기 전에** Pro로 전환한다. 순서는 Polar 승인 → Vercel Pro → production 배포 → 결제 활성화.
**이유**: Vercel 이용약관 §4와 Fair Use 가이드라인이 Hobby를 비상업적 개인 용도로만 허용하고, 상업적 사용의 첫 번째 예시가 "사이트 방문자로부터 결제를 요청하거나 처리하는 모든 행위"다. 회색지대가 아니다. 정책 위반으로 정지되면 `503 DEPLOYMENT_PAUSED`가 뜨고 자동 복구되지 않는다. 추가로 Hobby와 Pro 체험판은 약관상 **콘텐츠가 Vercel의 AI 모델 학습에 사용되고 제3자와 공유될 수 있어**, 거래 데이터를 다루는 서비스에는 부적합하다.
**트레이드오프**: 월 $20의 고정비가 발생한다. 전환 시점을 놓치면 약관 위반 상태로 운영된다. 심사 대기 기간에는 결제가 발생하지 않으므로 그동안은 Hobby로 버틴다.

### ADR-015: Polar production 심사를 step 1에서 제출한다
**결정**: preview 배포로 접근 가능한 URL이 나오는 즉시(step 1) production 심사를 제출하고, 나머지 구현과 병렬로 진행한다.
**이유**: 심사는 **최대 14일**이 걸리고, 샌드박스와 production은 완전히 분리된 서버라 계정·액세스 토큰·상품·webhook 시크릿 중 넘어오는 것이 하나도 없다. step 14에서 제출하면 구현 완료 후 2주를 더 기다리게 된다. Polar 문서는 동작하는 웹사이트와 설정된 상품이 있으면 승인이 빨라진다고 안내하므로, 목업 랜딩이라도 제출 조건은 충족된다.
**트레이드오프**: 제품이 완성되기 전 상태로 심사를 받는다. 심사 항목이 바뀌거나 반려되면 재제출이 필요하다.

### ADR-016: Polar webhook 서명 검증은 SDK에 위임한다
**결정**: 공식 SDK의 webhook 검증 유틸리티를 쓰고 HMAC 비교를 직접 구현하지 않는다.
**이유**: **2026-09-08 00:00 UTC 이후 발급된 시크릿은 Standard Webhooks 규격**을 따르고 그 이전은 Polar 자체 HMAC이다. 현재 샌드박스 시크릿은 구 방식, step 14에서 발급할 production 시크릿은 신 방식이므로 **같은 코드가 두 규격을 모두 만난다.** 직접 구현하면 production 전환일에 결제가 조용히 끊긴다.
**트레이드오프**: SDK 버전에 묶이고, 검증 실패 원인을 직접 들여다보기 어려워진다.

### ADR-017: LLM 품질 검증을 `npm test`에서 분리한다
**결정**: `npm test`는 LLM 호출을 전부 모킹해 결정적으로 유지하고, 실제 API로 분류 정확도를 재는 평가는 `npm run eval`로 분리해 수동 실행한다.
**이유**: Stop 훅이 매 턴 `lint && build && test`를 실행한다. 여기에 실제 호출이 섞이면 파일 하나 고칠 때마다 비용이 나가고, 모델이 답을 조금만 바꿔도 무관한 커밋에서 실패해 작업이 불가능해진다. 반대로 모킹만 두면 스키마는 통과하는데 분류 내용이 쓸모없는 상태를 걸러내지 못한다.
**트레이드오프**: 분류 품질 회귀가 자동으로 잡히지 않는다. 라벨링 샘플 20~30건의 정답을 사람이 검수하고 주기적으로 직접 돌려야 한다.
